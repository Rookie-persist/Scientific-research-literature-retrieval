# D1 基线记录：面向科研文献的引用可核验 RAG

> 执行日期 2026-10-20 · 语料 L0（20 篇 arXiv）· 20 题（16 道 ORB 金标 + 4 道负样本）
> 配置：bge-small-en-v1.5（384 维）· qwen35-9b-16k（`num_ctx=16384`、`presence_penalty=0`）· `max_tokens=4096` · 启用 `CitationPolicyCapability`

## 一、结论先行

**在这个语料上，瓶颈不在检索，而在解析质量与生成纪律。**

检索 recall@5 = **99.5%**、MRR = 0.991、Top-1 带页码率 100%——几乎不存在"检不到"的问题。但 16 道题里有 1 道答错（公式被模型编造）、1 道该答却拒答。答错的直接原因是 **13.3% 的块在解析阶段就丢了公式**，与检索无关。

这意味着项目重心要从"改进检索"移到"**保证答案能被引用支撑**"，这恰好是 M3 的位置。

## 五、三个发现（均已在代码/数据层核实）

### 发现 1：公式在解析阶段就丢了，占 13.3% 的块

425 / 3,193 个块含 `<!-- formula-not-decoded -->`，波及 15/20 篇。最严重的一篇 79/146 = 54%。

第 4 题的原文块长这样：

```
<!-- formula-not-decoded --> As < is a function of time, solving Eq. 1 for < can determine the WTT ...
In Eq. 2, 2< ! = 0.21; < = 0.32. Therefore, with < = √2"5 <!-- formula-not-decoded -->
```

检索完全正确（Top-1、正确章节、正确页码），但块里没有公式，模型于是**按上下文编了一个看起来合理的公式**。这正是 M3 要拦的"无依据断言"，也说明**引用存在 ≠ 引用支撑**。

**可修复，且已实测**：Docling 的 `do_formula_enrichment=True` 能把公式还原为 LaTeX。同一页（p.5）开启后输出：

```
$$W T T = \frac { ( 0 . 3 2 ) ^ { 2 } } { 2 D }$$
```

与金标完全一致，占位符计数从 8 降到 0。

**但 haiku.rag 没有暴露这个开关**：`ConversionOptions` 里没有 `do_formula_enrichment` 字段，`docling_local.py::_build_pipeline_options` 也没有设置它。要开启只能改代码（子类化转换器并替换 `get_converter`，约 20 行）。

**代价**：实测每页边际约 **15 秒**（2 页 47.7 s、1 页 32.7 s，差值即单页成本）。一篇 15 页的论文从 45 秒涨到约 4 分钟，**慢 5 倍**。20 篇约 75–80 分钟。

### 发现 2：`score` 是 RRF 融合分，不能当相关性用

代码里 `chunk.py:316` 用 `RRFReranker()`（默认 k=60），混合检索（vector + FTS）后分数为 `Σ 1/(60+rank)`。实测分数只有几个离散值：

- `0.0164` = 1/61 → 在某一路排第 1
- `0.0328` = 2/61 → 在两路都排第 1

**后果**：分数不携带语义相似度，只反映两路排序的一致性。所以——

- **无法用分数阈值判断"该不该拒答"**。实测负样本 Top-1 为 0.0323 / 0.0164 / 0.0164 / 0.0164，而正样本 Top-1 的 min = 0.0164、p10 = 0.0320、median = 0.0328，**分布完全重叠**。metformin 那道负样本（0.0323）甚至高于正样本的 p10。
- 任何"低分就拒答"的策略在这个架构下都不可能work，除非换掉 RRF 保留原始余弦分，或引入 cross-encoder 打分。

这一条直接影响 M3 的设计：**证据充分性判定不能依赖 score**，只能用 LLM 判定或交叉编码器。

### 发现 3：参考文献挤占远没有预期严重

Top-5 中参考文献块平均只有 **0.39 个（7.8%）**。此前假设"参考文献污染会挤占 Top-K"，在 ORB/arXiv 这类语料上**不成立**。

原因推测：ORB 的题目基本都能在单篇论文的正文段落里找到直接答案，向量检索对"问题—段落"的匹配本就偏向正文；参考文献条目句式高度雷同（作者+标题+会议），反而不易与具体问题匹配。

**对 M2 的影响**：降权参考文献的收益上限只有约 8% 的槽位，且这 8% 大多发生在本来就答对的题上。**M2 的优先级应下调**。

### 附带发现：拒答的延迟是正题的 4 倍

负样本均值 82.5 秒，正题 20.9 秒。原因是 `rag.md` 指令里那条规则——"结果明显不匹配就换关键词再搜一次"——**恰好只在不可答题上触发**，等于把成本加在了最不该加的地方。这是 M1（查询理解）的一个天然切入点：如果能先判断"该不该答"，就不必先烧两轮检索。

## 六、对计划的修正建议

| 项 | 原计划 | 建议 |
|---|---|---|
| M2 参考文献降权 | 三模块之一 | **降级为可选**。实测收益上限 7.8%，不足以支撑一个模块。空出的时间给 M3 |
| 公式识别 | 未列入 | **列为可选增强档**。修的是实测答错的那道题，但摄取慢 5 倍，适合最终档而非开发档 |
| M3 证据判定 | 用判定结果触发重检索 | 判据**不能用 score**（发现 2），必须走 LLM 或 cross-encoder |
| M1 查询理解 | 缩写/术语扩展 | 增加一个价值点：**先判可答性**，避免在不可答题上烧两轮检索（4 倍延迟） |

## 七、复现

```bash
export HAIKU_RAG_CONFIG_PATH=./haiku.rag.yaml

# 检索诊断（不调用 LLM，约 1 分钟）
.venv/Scripts/python.exe scripts/diag_retrieval.py \
  --db ./dbs/smoke.lancedb --subset subset_20 --limit 5 --out eval/retrieval-diag.json

# 问答基线（20 题，约 10 分钟）
.venv/Scripts/python.exe -u scripts/run_baseline.py \
  --db ./dbs/smoke.lancedb --subset subset_20 --out eval/baseline.jsonl --policy
```

产物：`eval/baseline.jsonl`（逐题记录）、`eval/baseline-summary.json`（汇总）、`eval/retrieval-diag.json`（检索诊断）。
